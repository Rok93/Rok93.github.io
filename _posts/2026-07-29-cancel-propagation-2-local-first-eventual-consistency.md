## 취소 한 번에 쓰기가 두 군데 일어난다

결제 취소 API를 만들면서, "쓰기(저장)가 두 군데서 일어난다"는 사실과 마주했습니다.

1. **우리 DB**의 결제 상태를 "취소"로 바꾸기 (로컬, 즉 우리가 통제하는 내부 저장소)
2. **외부 결제 게이트웨이(PG사)** 에 취소 전파하기 (원격, 네트워크·실패·지연이 있는 남의 시스템)

가장 단순한 방법은 이 둘을 **한 트랜잭션**(전부 성공 아니면 전부 취소로 묶는 단위)에 넣는 겁니다. 그런데 그러면 문제가 생깁니다. 외부 PG사가 느리거나 잠깐 죽으면, **사용자의 취소 응답까지 같이 느려지고 실패**합니다. 남의 시스템 사정에 내 응답이 볼모로 잡히는 거죠.

## 개념 ① 두 쓰기는 성격이 다르다

먼저 두 쓰기가 얼마나 다른지 정리해 봅시다.

| | 로컬 상태 변경 | 외부 전파 |
|---|---|---|
| 실패율 | 낮음 (내 DB) | 높음 (네트워크·외부 장애) |
| 지연 | 밀리초(ms) 수준 | 수백 ms ~ 타임아웃 |
| 사용자가 기다릴 만한가 | 예 | 아니오 |

핵심은 마지막 줄입니다. 사용자에게 중요한 건 **"취소 접수됐습니다"** 까지입니다. 외부 PG 전파까지 눈앞에서 기다릴 이유가 없습니다. 외부 전파는 **뒤에서 따라오면 됩니다.**

## 개념 ② local-first: 로컬은 즉시 확정, 외부는 커밋 후에

그래서 택한 방식이 **"로컬 먼저(local-first)"** 입니다. 이름 그대로, 내가 통제하는 로컬부터 확정하고 외부는 나중으로 미룹니다.

- 요청을 처리하는 흐름에서: 로컬 상태를 "취소"로 바꾸고 **바로 커밋 → 사용자에게 즉시 응답.**
- 커밋이 끝난 뒤(`AFTER_COMMIT`) **이벤트**로 외부 전파를 트리거. (이벤트 = "취소됐다"는 사건을 알리면, 그에 반응하는 코드가 따로 실행되는 구조)

아래 코드가 하는 일: 결제를 로컬에서 취소 확정하고, "취소됐다"는 이벤트를 발행합니다. 외부 전파는 이 이벤트를 받아 커밋 후에 실행됩니다.

```java
@Transactional
public void markCanceled(String paymentKey) {
    PaymentCancelRequest req = repository.findByPaymentKey(paymentKey)
            .orElseThrow(() -> new BusinessException(NOT_FOUND));
    req.cancel();                                        // 로컬 즉시 확정
    eventPublisher.publishEvent(new PaymentCanceledEvent(paymentKey));  // 전파는 커밋 후
}
```

## 개념 ③ 커밋 후 전파 = 최종적 일관성 (짧은 어긋남을 받아들인다)

이 방식에는 대가가 있습니다. 로컬은 이미 "취소됨"인데 외부 PG는 아직 "취소 안 됨"인 **짧은 구간**이 생깁니다. 두 시스템이 잠깐 어긋나는 거죠.

이렇게 "잠깐 어긋났다가 결국 같아지는" 걸 **최종적 일관성(eventual consistency)** 이라고 합니다. 반대는 **강한 일관성(strong consistency)** — 항상 어느 순간에도 어긋나지 않는 것.

이 결제 취소 도메인에서는 그 짧은 어긋남이 치명적이지 않으므로 최종적 일관성으로 충분합니다.

> 판단 기준 하나: 만약 그 값을 **읽고 곧바로 허용/거부를 가르는 로직**이 있었다면(예: 취소 여부를 보고 즉시 다른 결제를 막아야 한다면) 이야기가 다릅니다. 그런 값을 **load-bearing(하중을 받는, 즉 다른 판단이 이 값에 기대는) 상태**라고 부르고, 그때는 강한 일관성이 필요합니다. 우리 경우는 그렇지 않았습니다.

## 개념 ④ fail-safe: 외부 전파 실패는 "아직 취소 안 됨"으로 남긴다

외부는 언제든 실패할 수 있습니다. 그래서 **실패했을 때 어떤 상태로 남는가**를 설계의 중심에 뒀습니다.

핵심은 **순서**입니다. 전파를 이 순서로 합니다: **외부(PG) 취소 성공 → 그 다음에 로컬의 하위 결제 건을 취소로 전이.** 그래서 외부가 실패하면, 하위 결제 건은 취소로 넘어가지 않고 "아직 취소 안 됨" 상태로 **그대로 남습니다.**

이게 왜 좋을까요? 나중에 **"상위 결제=취소인데 하위 건=취소 안 됨"** 인 데이터를 훑기만 하면, **재처리해야 할 대상**을 정확히 골라낼 수 있기 때문입니다. 반대로 로컬을 먼저 취소해 버리고 외부가 실패하면, 겉보기엔 다 취소된 것 같아서 **무엇을 다시 처리해야 하는지 추적할 단서가 사라집니다.**

아래 코드가 하는 일: 취소할 하위 건이 있을 때만 외부 PG를 호출하고, **외부가 성공한 경우에만** 로컬 하위 건을 취소로 전이합니다. 실패하면 로그만 남기고 상태는 건드리지 않습니다.

```java
public void propagate(String paymentKey) {
    // (1/3)에서 다룬 master 강제 조회 — 방금 커밋한 결제 건을 누락 없이 읽는다
    List<Payment> payments = processor.findPayments(paymentKey);
    boolean hasCancelable = payments.stream().anyMatch(p -> !p.isCanceled());
    if (!hasCancelable) return;                          // 전파할 게 없으면 외부 호출 생략(멱등)

    try {
        var res = paymentGatewayClient.cancel(paymentKey, CUSTOMER_REQUEST);
        if (res.isSuccess()) {
            processor.markPaymentsCanceled(paymentKey);  // 외부 성공 후에만 로컬 전이
            return;
        }
        log.error("외부 취소 실패. 수동 확인/재처리 필요: paymentKey={}", paymentKey);
    } catch (Exception e) {
        log.error("외부 취소 전파 중 예외. 수동 확인/재처리 필요: paymentKey={}", paymentKey, e);
    }
}
```

여기서 `if (!hasCancelable) return;`은 **멱등성(idempotency, 같은 요청을 여러 번 해도 결과가 같음)** 을 위한 장치입니다. 이미 다 취소됐거나 취소할 게 없으면 외부를 다시 부르지 않습니다.

## 개념 ⑤ 일부러 아직 안 한 것과 그 이유

설계에는 "지금 하지 않기로 한 것"도 있습니다. 이걸 명시하는 게 중요합니다.

- **@Async 비동기화**: 커밋 후 리스너는 여전히 요청 흐름과 같은 스레드에서 순서대로 실행됩니다. 여러 건을 한 번에 취소하면 외부 호출이 하나씩 순차로 나가 느려질 수 있습니다. 이건 별도 작업으로 뺐습니다. 설계가 확정되지 않은 상태에서 성급히 비동기를 넣지 않기로 했습니다.
- **자동 재처리 스윕**: 지금은 실패를 로그로 남기고 사람이 확인합니다. 개념 ④에서 만든 "어긋난 상태를 훑어 재처리"하는 배치는 후속 과제로 남겼습니다.

→ 원칙은 하나입니다. **"지금 확정할 수 있는 것만 확정하고, 나머지는 나중에 바꾸기 쉬운 형태로 남긴다."**

## 코드로 검증한 과정

이 설계의 핵심 결정 — "외부 성공 후에만 로컬을 전이한다" — 은 말로 정한 게 아니라 **재처리 대상의 정의**에서 역으로 도출했습니다.

재처리 대상을 문장이 아니라 **상태 조합**으로 못 박았습니다: `상위 결제 = 취소 && 하위 건 ≠ 취소` → 재처리 대상. 이 정의가 성립하려면 하위 건은 **외부가 성공한 뒤에야** 취소로 바뀌어야 합니다. 그래서 코드의 전이 순서(외부 성공 → 로컬 전이)를 그 정의에 맞춰 고정했습니다. 순서가 곧 계약인 셈입니다.

## 한 줄 교훈

> **사용자에게 중요한 것만 트랜잭션에 넣어 즉시 확정하라. 외부 전파는 커밋 후 이벤트로 미루되, "실패가 곧 재처리 대상으로 드러나는 상태 조합"이 남도록 전이 순서를 설계하라.**
