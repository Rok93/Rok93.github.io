## N+1 문제가 뭔가 — 목록 1번 + 건건이 N번

먼저 상황을 그림으로 잡자. 엔티티 두 개가 있다. `Order`(주문)는 `Member`(회원)를 **다대일(@ManyToOne)**로 참조한다. 여러 주문이 한 회원에 매달린다는 뜻이다.

이 코드가 하는 일: 주문을 전부 조회한 뒤, 각 주문에 걸린 회원의 이름을 꺼낸다.

```java
List<Order> orders = orderRepository.findAll();   // ① 주문 목록 조회
for (Order order : orders) {
    System.out.println(order.getMember().getName());  // ② 회원 이름 접근
}
```

여기서 SQL은 몇 번 나갈까? 직관적으로는 "주문 한 번, 회원 한 번" 두 번일 것 같다. 하지만 실제 로그는 이렇다.

```sql
-- ① findAll()
SELECT * FROM orders;                       -- 1번, 주문 100건 반환

-- ② 반복문에서 order.getMember() 접근할 때마다
SELECT * FROM member WHERE id = 1;          -- 주문 1의 회원
SELECT * FROM member WHERE id = 2;          -- 주문 2의 회원
SELECT * FROM member WHERE id = 3;
...                                          -- 주문마다 한 번씩
SELECT * FROM member WHERE id = 100;        -- 주문 100의 회원
```

주문 목록 조회 **1번**, 회원 조회 **N번(=100)**. 합쳐서 **N+1번(=101)**. 이게 이름의 유래다. 주문이 1,000건이면 쿼리는 1,001번, 10,000건이면 10,001번으로 **데이터가 늘수록 선형으로 폭발**한다. 각 쿼리 자체는 빠를지 몰라도, 네트워크 왕복이 수백·수천 번 쌓이면 응답이 눈에 띄게 느려진다.

## 왜 이런 일이 벌어지나 — 지연 로딩과 프록시

핵심 원인은 **지연 로딩(lazy loading, 실제로 쓸 때까지 조회를 미루는 방식)**이다. JPA에서 `@ManyToOne`·`@OneToMany` 같은 연관관계는 로딩 전략을 정할 수 있는데, 기본적으로 `@OneToMany`는 지연 로딩이고 `@ManyToOne`도 대개 지연 로딩으로 두는 걸 권장한다.

지연 로딩이면 `findAll()`로 주문을 가져올 때 **회원은 함께 조회하지 않는다.** 대신 `order.getMember()`가 돌려주는 건 진짜 회원 객체가 아니라 **프록시(proxy, 실제 객체인 척하는 대리 껍데기)**다. 이 프록시의 실제 값(이름 등)에 처음 손을 대는 순간, JPA가 "아, 이제 진짜 데이터가 필요하구나" 하고 그때서야 `SELECT`를 날린다. 이걸 **초기화(initialization)**라 한다.

그래서 반복문이 문제가 된다. 주문 100건을 돌면서 `getMember().getName()`을 100번 부르면, 프록시 초기화도 100번 일어나고, 쿼리도 100번 나간다. 지연 로딩 자체는 "안 쓸 데이터를 미리 안 읽는" 좋은 전략이지만, **목록을 돌며 연관 데이터를 건건이 쓰는** 패턴을 만나면 정확히 N+1로 터진다.

> 참고: 반대로 **즉시 로딩(eager loading)**으로 바꾸면 어떨까? `findAll()` 시점에 회원을 함께 읽긴 하지만, JPA가 이를 조인 한 방이 아니라 **주문마다 별도 SELECT**로 처리하는 경우가 많아 N+1이 그대로 재현된다. 즉 로딩 전략을 즉시로 바꾸는 건 근본 해법이 아니다. 해법은 **어떻게 조회하느냐**에 있다.

## 페치 조인 — 연관 데이터를 조인으로 한 번에

해법은 **페치 조인(fetch join)**이다. 이름 그대로, 연관 엔티티를 **조인해서 한 번의 쿼리로 함께(fetch) 가져오는** JPQL(JPA 전용 쿼리 언어) 문법이다.

이 코드가 하는 일: 주문을 조회하면서 회원을 조인으로 함께 읽어 온다.

```java
@Query("SELECT o FROM Order o JOIN FETCH o.member")
List<Order> findAllWithMember();
```

일반 `JOIN`과 달리 `JOIN FETCH`는 **조인한 대상을 결과 엔티티에 실제로 채워서** 돌려준다. 실행되는 SQL은 딱 한 번이다.

```sql
SELECT o.*, m.*
FROM orders o
JOIN member m ON o.member_id = m.id;   -- 1번으로 끝
```

이제 `order.getMember().getName()`을 아무리 불러도 추가 쿼리가 나가지 않는다. 회원 데이터가 이미 엔티티 안에 **채워진(초기화된)** 상태이기 때문이다. 쿼리 101번이 **1번**으로 줄었다.

## 상세 예시 — before/after로 보는 쿼리 수

숫자로 확인하자. 주문 100건, 각 주문에 회원 1명이 걸린 상황이다.

| 방식 | 주문 조회 | 회원 조회 | 총 쿼리 |
|---|---|---|---|
| `findAll()` + 반복 접근 (지연 로딩) | 1 | 100 | **101** |
| `JOIN FETCH` (페치 조인) | 1 (조인) | 0 (함께 읽음) | **1** |

Hibernate(대표적 JPA 구현체)의 SQL 로그로 보면 차이가 분명하다.

**before — N+1이 터지는 로그 (일부):**
```
Hibernate: select o.* from orders o
Hibernate: select m.* from member m where m.id=?
Hibernate: select m.* from member m where m.id=?
Hibernate: select m.* from member m where m.id=?
... (member select가 100줄 반복)
```

**after — 페치 조인 로그:**
```
Hibernate: select o.*, m.* from orders o inner join member m on o.member_id=m.id
```

로그가 100여 줄에서 **한 줄**로 줄었다. 이게 페치 조인의 효과다.

### 주의: 컬렉션 페치 조인의 함정

페치 조인이 만능은 아니다. `@OneToMany`처럼 **컬렉션(1:N)을 페치 조인**하면 두 가지 함정이 있다.

- **중복 행** — 한 주문에 주문상품 3개가 걸려 있으면, 조인 결과는 주문이 3줄로 뻥튀기된다(카테시안 곱). 해결하려면 JPQL에 `DISTINCT`를 붙여 애플리케이션 레벨에서 중복 엔티티를 걸러 준다.
- **페이징 불가** — 컬렉션 페치 조인에 `LIMIT`을 걸면, DB에서 자르는 게 아니라 **전체를 메모리로 읽어 와 잘라** 위험하다(Hibernate가 경고 로그를 남긴다). 이럴 땐 페치 조인 대신 `@BatchSize`(연관 데이터를 IN 절로 묶어 한 번에 N건씩 조회)나 `default_batch_fetch_size` 설정으로 N+1을 **N/배치 수준으로 완화**하는 편이 안전하다.

정리하면, **다대일(N:1) 단순 참조는 페치 조인이 정석**이고, **일대다(1:N) 컬렉션은 `DISTINCT`·배치 사이즈를 함께 고려**해야 한다.

## 정리 — 목록을 돌기 전에 "쿼리 몇 번?"을 묻기

1. **N+1 문제** — 목록 1번 조회 + 항목마다 연관 조회 N번 = 1+N번 쿼리 폭발.
2. **원인** — 지연 로딩된 연관관계를 반복문에서 건건이 초기화하기 때문.
3. **해법** — `JOIN FETCH`로 연관 데이터를 조인 한 번에 함께 읽는다.
4. **주의** — 컬렉션 페치 조인은 `DISTINCT`·페이징 제약·배치 사이즈를 함께 챙긴다.

한 줄 교훈: **목록을 순회하며 연관 데이터를 꺼내는 코드를 짤 때는, SQL 로그부터 켜고 "쿼리가 몇 번 나가나"를 눈으로 확인하라.** N+1은 로직이 멀쩡해 보여서 로그를 안 보면 놓치기 쉽다.
