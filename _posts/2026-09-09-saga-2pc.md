주문 하나를 처리하는 데 서비스 세 개가 관여한다. 결제 서비스가 돈을 빼고, 재고 서비스가 물건을 잡고, 배송 서비스가 배차를 건다. 옛날처럼 이 셋이 **한 데이터베이스**에 있었다면 트랜잭션(여러 작업을 *전부 성공 아니면 전부 취소*로 묶는 단위) 하나로 감쌌을 것이다. 그런데 마이크로서비스(microservice — 기능별로 쪼갠 독립 서비스)로 나눠 놓으니 데이터베이스가 셋으로 흩어졌다. **한 트랜잭션으로 묶을 수 없는데, "전부 성공 아니면 전부 취소"는 여전히 지켜야 한다.** 이 문제를 푸는 대표적인 두 방식이 **2PC(Two-Phase Commit — 2단계 커밋)**와 **Saga(사가)**다. 이 글은 둘이 각각 어떻게 동작하는지, 무엇을 얻고 무엇을 포기하는지를 따라간다.

## 문제부터 — 왜 흩어진 DB는 트랜잭션이 안 되나

**무엇**이 문제인지부터. 하나의 데이터베이스 안에서는 커밋(트랜잭션을 확정 저장) 하나로 여러 작업을 원자적(atomic — 쪼갤 수 없이 전부 아니면 전무)으로 묶을 수 있다. DB 엔진이 로그와 락으로 이를 보장한다.

하지만 결제·재고·배송이 **각자 다른 DB**를 쓰면, 각 DB의 커밋은 자기 것만 책임진다. 결제 DB는 커밋됐는데 재고 DB가 실패하면? 결제 DB는 이미 확정돼서 되돌릴 방법이 없다. **돈은 빠졌는데 물건은 안 잡힌** 상태가 남는다. 이 "부분 성공(partial failure)"을 막는 게 분산 트랜잭션(distributed transaction — 여러 시스템에 걸친 하나의 논리적 거래)의 핵심 과제다.

## 2PC — 심판 한 명이 모두에게 묻고 한 번에 확정한다

**무엇**. 2PC는 **코디네이터(coordinator — 조율자)** 한 명이 참가자(participant — 각 DB/서비스)들을 지휘해 딱 두 단계로 커밋을 맞추는 방식이다.

- **1단계 — 준비(prepare):** 코디네이터가 모든 참가자에게 "커밋할 준비 됐나?"를 묻는다. 각 참가자는 실제로 작업을 해보고 **로그에 적어 잠가둔 뒤** "예(ready)" 또는 "아니오(abort)"로 답한다. 이때 아직 **확정은 안 한다**. 되돌릴 수 있는 상태로 대기만 한다.
- **2단계 — 커밋/중단(commit/abort):** **모두가 "예"**라고 답했으면 코디네이터가 "전부 커밋" 명령을 내린다. 한 명이라도 "아니오"면 "전부 중단"을 내린다.

**왜** 이렇게 하나. 모든 참가자를 "준비됐지만 아직 확정 전"인 지점에 세워 두면, 그 순간엔 **누구든 커밋도 롤백도 할 수 있다**. 그 상태를 확인한 뒤에만 확정하니 전원이 같은 결정을 따르게 된다.

**2PC의 대가.** 강력하지만 값이 비싸다.

- **잠금이 오래 걸린다(blocking).** 1단계에서 자원을 잠근 뒤 2단계 명령이 올 때까지 **계속 잠긴 채로 대기**한다. 참가자가 많거나 느리면 락 유지 시간이 길어져 처리량이 떨어진다.
- **코디네이터가 단일 장애점.** 1단계 뒤 코디네이터가 죽으면, 참가자들은 "커밋해야 하나 롤백해야 하나"를 모른 채 **잠긴 상태로 멈춘다(in-doubt)**. 이 취약점이 2PC를 대규모 마이크로서비스에서 꺼리게 만드는 핵심 이유다.

## Saga — 도장을 차례로 찍고, 틀리면 되감는다

**무엇**. Saga는 하나의 큰 거래를 **여러 개의 로컬 트랜잭션(local transaction — 서비스 하나가 자기 DB에서 바로 커밋하는 작은 트랜잭션)**으로 쪼갠다. 각 단계는 **바로 커밋**한다 — 잠가두지 않는다. 대신 어느 단계가 실패하면, 이미 커밋된 앞 단계들을 **보상 트랜잭션(compensating transaction — 앞의 작업을 되돌리는 반대 작업)**으로 하나씩 취소한다.

**왜** 되돌리는 방식을 쓰나. 흩어진 DB는 남의 커밋을 물리적으로 롤백할 수 없다. 그래서 "롤백" 대신 **의미상 반대되는 새 작업**으로 상쇄한다. 결제 커밋을 못 지우니 **환불**을 하고, 재고 차감을 못 지우니 **재고 복원**을 한다. 결과적으로 없던 일처럼 만든다.

예를 들어 주문 Saga의 정상 흐름과 실패 흐름은 이렇다.

- 정상: `결제 승인 → 재고 차감 → 배송 배차` (세 로컬 트랜잭션 각각 커밋)
- 배송에서 실패: `배송 실패 → 재고 복원(보상) → 결제 환불(보상)` — **역순으로** 되감는다.

## Saga를 조율하는 두 방식 — 오케스트레이션 vs 코레오그래피

Saga에서 "다음에 뭘 할지, 실패하면 뭘 되감을지"를 **누가 결정하느냐**로 두 스타일이 갈린다.

- **오케스트레이션(orchestration — 지휘형):** **오케스트레이터(orchestrator)**라는 중앙 조율자가 "결제 해라 → (성공) 재고 잡아라 → (실패) 결제 환불해라" 식으로 각 단계를 명령한다. 흐름이 한 곳에 모여 **추적·디버깅이 쉽다**. 대신 조율자 코드가 무거워진다.
- **코레오그래피(choreography — 안무형):** 중앙 지휘자가 없다. 각 서비스가 **이벤트(event — "결제됨" 같은 사실 통지)**를 발행하고, 다음 서비스가 그 이벤트를 듣고 알아서 자기 일을 한다. 서비스 간 결합이 느슨하지만, 전체 흐름이 여러 서비스에 흩어져 **"지금 어디까지 됐지"를 파악하기 어렵다**.

**이 코드가 하는 일:** 오케스트레이션 방식에서 배송 단계가 실패했을 때, 앞서 성공한 단계들을 역순으로 보상 호출하는 뼈대다.

```java
// 오케스트레이터가 단계를 순서대로 실행하고, 실패하면 완료된 단계만 역순 보상
List<Step> completed = new ArrayList<>();
try {
    payment.charge(order);   completed.add(PAYMENT);  // 각 단계는 자기 DB에 즉시 커밋
    stock.reserve(order);    completed.add(STOCK);
    delivery.dispatch(order); completed.add(DELIVERY); // 여기서 예외 발생 가정
} catch (Exception e) {
    // 완료된 단계만, 실행의 역순으로 되감는다
    Collections.reverse(completed);
    for (Step s : completed) {
        switch (s) {
            case DELIVERY -> delivery.cancel(order);  // 배송 취소
            case STOCK    -> stock.restore(order);    // 재고 복원(보상)
            case PAYMENT  -> payment.refund(order);   // 결제 환불(보상)
        }
    }
}
```

## Saga가 포기하는 것 — 격리성과 "잠깐 어긋난 상태"

Saga는 잠금을 안 하는 대신 **격리성(isolation — 동시에 도는 다른 거래가 중간 상태를 못 보게 막는 성질)**을 포기한다. 결제는 커밋됐는데 배송 보상이 아직 안 끝난 **그 잠깐 사이**, 다른 거래가 "결제는 됐고 배송은 취소 중인" 어정쩡한 상태를 볼 수 있다. 이걸 최종 일관성(eventual consistency — 지금 당장은 어긋나 있어도 시간이 지나면 결국 맞춰지는 상태)이라 부른다.

그래서 Saga 설계에는 두 가지가 거의 필수다.

- **멱등성(idempotency — 같은 요청을 여러 번 받아도 결과가 한 번과 같은 성질).** 이벤트가 재전송되거나 보상이 두 번 불릴 수 있어, 각 단계와 보상이 중복 실행에도 안전해야 한다.
- **보상 가능 설계.** "이미 발송된 물건"처럼 되돌릴 수 없는 작업은 Saga 뒤쪽에 배치하거나, 아예 취소 가능한 형태(예: 발송 전 대기)로 바꿔야 한다.

정리하면 선택 기준은 이렇다.

- **참가자가 적고, 짧은 시간에 강한 일관성이 꼭 필요하며, 잠금 대기를 감당할 수 있다** → 2PC가 개념적으로 단순하다. (단일 조직 내 소수 DB 등)
- **참가자가 많고, 오래 걸리는 거래이며, 각 서비스의 독립성과 확장성이 중요하다** → Saga. 대부분의 마이크로서비스 환경이 여기에 해당해, 실무에서는 Saga가 기본 선택지가 되는 경우가 많다.

## 한 줄 교훈

**2PC는 "모두 잠그고 한 번에 확정"으로 강한 일관성을 사고, Saga는 "차례로 커밋하고 틀리면 되감기"로 확장성을 산다.** 흩어진 DB에서 롤백은 공짜가 아니다 — 잠금으로 값을 치르거나, 보상 로직으로 값을 치른다. 어느 쪽을 낼지가 곧 설계 결정이다.
