> 📝 이 글은 X(트위터)에 올라온 한 홍보성 스레드(TypeSafe AI의 *Jev* 소개)를 읽고 개념만 추려 정리한 것입니다. 본문에 나오는 속도·비용 수치(“400배 저렴”, “7초” 등)는 전부 **판매사·사용자 데모 기준**이라 독립 검증된 값이 아닙니다. 제품 광고가 아니라, 그 밑에 깔린 **설계 아이디어**가 쓸 만해서 남깁니다.

## 시작: 비싼 모델이 "예/아니오"에 돈을 쓰고 있다

요즘 AI 에이전트(스스로 도구를 골라 쓰며 일을 처리하는 프로그램)는 대부분 이런 반복문 안에서 돕니다.

1. LLM(대형 언어 모델, 문장을 생성하는 그 모델)이 "다음에 뭘 할지" 정한다
2. 도구가 실제로 실행한다
3. 모델이 결과를 보고 "됐나?" 판단한다
4. 끝날 때까지 1번으로 돌아간다

문제는 이겁니다. 저 반복문에서 **매 판단마다 LLM 호출이 한 번씩 나간다**는 것. 그런데 "소스가 충분한가?", "다음 워커는 리서처인가 작성자인가?", "이 초안 검토 보내도 되나?" 같은 판단은 **글을 지어낼 필요가 없습니다.** 목록에서 하나 고르거나, 점수를 매기거나, 예/아니오를 답하면 끝이죠.

문장을 만드는 값비싼 모델에게 "예/아니오"를 시키는 건, 에세이 작가한테 O/X 채점을 맡기는 것과 비슷합니다. 할 수는 있는데, 과합니다.

## 핵심 아이디어: "결정 전용 모델"을 따로 둔다

스레드가 소개하는 Jev는 스스로를 **"System One 모델"**이라 부릅니다. 심리학에서 빌린 표현인데, 사람의 사고를 *System 1(빠르고 직관적인 즉답)* 과 *System 2(느리고 논리적인 숙고)* 로 나눈 데서 따왔습니다. LLM이 System 2(숙고형 생성)라면, 이 모델은 System 1(즉답형 결정) 역할을 맡습니다.

작동 방식은 단순합니다.

- **입력**: 현재 상태(state) + 미리 정의한 질문
- **출력**: 확률이 붙은 **타입이 정해진 답**(정해진 보기 중 하나)

문장 생성도, 챗도, 추론 과정 서술도 없습니다. 오직 **"정해진 보기 중에 뭘 고를지"만** 답합니다. 대신 그걸 아주 빠르고 싸게 한다는 게 세일즈 포인트고요.

## 그래서 뭘 어디에 맡기나 — 3분할

이 글에서 가장 오래 남길 만한 건 이 분류 규칙 하나입니다.

- **텍스트를 만드는 일** → LLM에게 (조사, 문단 작성, 코드 생성)
- **보기에서 고르거나·점수 매기거나·예/아니오** → 결정 모델에게 (라우팅, 관련도 점수, 승인)
- **정확한 규칙** → 그냥 코드로 (예: "10번 행동하면 멈춤" 같은 건 모델 쓸 필요 없음)

"생각(thinking)"과 "결정(deciding)"을 분리하는 겁니다. 지금까지는 둘 다 같은 LLM이 뭉뚱그려 처리했는데, 결정 부분만 떼어내자는 거죠.

## 질문은 세 종류면 충분하다

스레드는 결정 질문을 세 가지 형태로 정리합니다. 개념만 보면 이렇습니다.

- **Choice(선택)**: 보기 목록에서 하나 고르기 — "다음 워커는? [리서처 / 작성자 / 검토]"
- **Score(점수)**: 정해진 척도로 점수 매기기 — "이 요청 긴급도는? [낮음 / 중간 / 높음 / 심각]"
- **yes/no**: 예/아니오 — "사람 검토 없이 실행해도 안전한가?"

아래는 이 세 가지를 **한 번의 호출에 묶어** 보내는 예시입니다. 상태 하나를 놓고 워커 선택·긴급도·안전 여부를 동시에 물어봅니다. (질문끼리는 서로의 답을 못 봅니다. 그래서 서로 독립적인 것만 묶습니다.)

```python
result = client.system_one(
    state=state,
    questions={
        "next_worker": Choice(              # 보기 중 하나
            instructions="다음 단계를 고른다.",
            criteria={...},
        ),
        "urgency": Score(                   # 척도 점수
            instructions="요청 긴급도를 매긴다.",
            labels=["low", "medium", "high", "critical"],
        ),
        "safe_to_run": Noul(                # 예/아니오
            instructions="사람 검토 없이 실행해도 안전한가.",
        ),
    },
)
```

한 가지 실전 팁도 나옵니다. **필드 이름(`safe_to_publish` 같은 것)에 기대지 말 것.** 모델은 그 이름을 보지 않습니다. 실제 판단 기준은 질문 설명(`instructions`)과 보기 설명에 또박또박 적어야 합니다.

## 어디에 쓰나 — 실제로 나온 사례들

개념만으로는 감이 안 오니, 스레드가 든 활용 예를 몇 개 옮깁니다. (수치는 데모 기준입니다.)

- **브라우저 조작**: 매 단계 "다음 클릭 대상"을 결정 모델이 고르게 함
- **문서 분류**: 논문/이메일을 정해진 카테고리로 분류
- **모델 라우팅**: 쉬운 작업은 싼 모델, 어려운 작업은 강한 모델로 — "가장 싼 모델로 처리 가능한가?"를 결정
- **컨텍스트 압축**: 이게 흥미로웠는데, 지금까지 대화 압축은 "요약해줘" 프롬프트를 LLM에 던지는 방식이었습니다. 대신 **각 도구 호출의 관련도를 점수 매겨 필요 없는 걸 버리는** 식으로 바꾸면, 요약이 아니라 "관련도 필터"가 됩니다. 훨씬 빠르다는 주장.

특히 마지막 압축 사례는, 결정 모델이 생성 모델을 **대체**하는 게 아니라 그 **주변의 잡일**을 걷어내는 방향이라 인상적이었습니다.

## 한 줄 교훈

에이전트를 만들 때, 반복문 안의 모든 "예/아니오·라우팅·점수"에 프런티어 모델(가장 크고 비싼 최신 모델)을 쓰고 있다면 한 번 세어보자. **그중 몇 개가 진짜로 '문장 생성'이 필요했나?**

> LLM은 조사·계획·작성에. 결정 모델은 라우팅·점수·승인에. 코드는 실행에.

"생각"과 "결정"을 나누는 것 — 새 제품을 사지 않더라도, 이 분류만 머릿속에 넣어두면 다음 에이전트 설계가 달라집니다.
