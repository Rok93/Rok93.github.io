로그인 기능을 만들다 보면 두 질문을 계속 만난다. "**이 사람이 누구인가?**"와 "**이 사람이 이걸 해도 되는가?**"다. 앞의 것을 **인증(Authentication — 신원 확인)**, 뒤의 것을 **인가(Authorization — 권한 확인)**라 부른다. 웹에서 이 두 질문을 다룰 때 가장 자주 나오는 이름이 **OAuth 2.0**과 **JWT**다. 둘은 자주 같이 쓰여서 한 덩어리로 오해받지만, 사실 하는 일이 다르다. OAuth 2.0은 "비밀번호를 넘기지 않고 권한만 빌려주는 **절차**"이고, JWT는 "그 권한을 담아 들고 다니는 **토큰의 형식**"이다. 이 글은 둘을 따로 이해한 뒤, 실제 토큰 하나를 뜯어보고 위조해 보며 어디서 막히는지 확인한다.

## 예시 무대 — 사진 인화 앱

무대를 하나 정한다. **인화 앱**이 사용자의 **클라우드 사진함**에서 사진을 가져와 인화해 주는 서비스다.

가장 쉬운(그리고 가장 나쁜) 방법은 인화 앱이 사용자에게 "클라우드 아이디와 비밀번호를 알려 주세요"라고 하는 것이다. 이러면 세 가지 문제가 생긴다.

1. 인화 앱이 사진 읽기만 필요한데, 비밀번호로는 **사진 삭제·결제·계정 변경까지 전부** 할 수 있다.
2. 인화 앱 하나만 끊고 싶어도 **비밀번호를 바꾸는 것 말고는 방법이 없다.** 바꾸면 다른 앱도 다 끊긴다.
3. 인화 앱 서버가 털리면 **비밀번호 원본**이 샌다.

OAuth 2.0은 바로 이 문제를 풀려고 만들어졌다.

## OAuth 2.0 — 비밀번호 대신 "범위가 정해진 출입증"

### 무엇인가

**OAuth 2.0**은 2012년 RFC 6749로 표준화된 **권한 위임(delegated authorization) 프레임워크**다. 핵심 아이디어는 한 문장이다. **사용자는 비밀번호를 신뢰하는 곳(클라우드)에만 입력하고, 인화 앱은 그 결과로 "사진 읽기만 되는 토큰"을 받는다.**

등장인물은 넷이다.

| 역할 | 원어 | 예시에서 |
|---|---|---|
| 자원 소유자 | Resource Owner | 사진 주인(사용자) |
| 클라이언트 | Client | 인화 앱 |
| 인가 서버 | Authorization Server | 클라우드의 로그인·동의 담당 서버 |
| 자원 서버 | Resource Server | 클라우드의 사진 API 서버 |

인가 서버가 발급하는 토큰을 **액세스 토큰(access token — API를 호출할 때 내미는 출입증)**이라 한다. 액세스 토큰에는 **스코프(scope — 허용 범위, 예: `photos:read`)**와 **만료 시각**이 붙는다. 그래서 위 세 문제가 풀린다. 범위는 사진 읽기로 좁혀지고, 인화 앱 토큰만 따로 취소할 수 있고, 인화 앱은 비밀번호를 본 적이 없다.

### 주의 — OAuth 2.0은 "로그인 표준"이 아니다

OAuth 2.0 자체는 **인가**만 다룬다. 액세스 토큰은 "이 토큰으로 사진을 읽어도 된다"는 뜻이지 "이 토큰을 든 사람이 kim이다"라는 신원 증명이 아니다. "구글로 로그인" 같은 **인증**은 OAuth 2.0 위에 얹은 **OpenID Connect(OIDC)**가 담당한다. OIDC는 액세스 토큰과 함께 **ID 토큰(사용자가 누구인지 적힌 JWT)**을 하나 더 준다.

### 대표 흐름 — Authorization Code + PKCE

OAuth 2.0에는 토큰을 받는 방법(**그랜트 타입, grant type**)이 여럿 있다. 지금 사용자가 끼는 대부분의 경우에 권장되는 것은 **Authorization Code 그랜트 + PKCE**다. 예전에 쓰던 Implicit 그랜트(토큰을 브라우저 주소에 바로 실어 보내던 방식)와 Password 그랜트(앱이 비밀번호를 직접 받던 방식)는 2025년 발표된 OAuth 2.0 보안 모범 사례(RFC 9700)에서 쓰지 말라고 정리됐다.

왜 토큰을 바로 주지 않고 **인가 코드(authorization code — 짧게 살고 한 번만 쓰는 교환권)**를 먼저 줄까? ③은 브라우저 주소창을 거친다. 주소는 브라우저 기록, 로그, 다른 앱에 새기 쉽다. 그래서 여기엔 혼자서는 쓸모없는 교환권만 싣고, 진짜 토큰은 ④⑤처럼 인화 앱이 인가 서버와 **직접** 주고받는다.

그래도 교환권 자체를 누가 가로채면? 그걸 막는 게 **PKCE(Proof Key for Code Exchange, RFC 7636 — "코드를 요청한 사람이 교환하러 온 사람과 같은지" 증명하는 장치)**다.

이 계산이 하는 일: 인화 앱이 ① 직전에 비밀값을 만들고, 그 해시만 먼저 보낸다.
```text
code_verifier  = dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk        ← 앱만 아는 무작위 비밀값
code_challenge = BASE64URL(SHA256(code_verifier))
               = E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM        ← ①에서 보냄 (method=S256)
```

①에는 해시(`code_challenge`)만 보내고, ④에서 원본(`code_verifier`)을 낸다. 인가 서버는 원본을 해시해서 ①에서 받은 값과 같은지 본다. 코드를 가로챈 공격자는 원본을 모르고, 해시만 보고 원본을 거꾸로 알아낼 수 없으니 교환에 실패한다.

①에 함께 붙는 `state`도 있다. 앱이 무작위 값을 실어 보내고 ③에서 같은 값이 돌아오는지 확인해, 공격자가 꾸며낸 응답을 앱이 받아들이지 않게 한다.

## JWT — 서명된 "자기 소개서" 토큰

### 무엇인가

⑤에서 받은 액세스 토큰은 어떻게 생겼을까? OAuth 2.0은 토큰 형식을 정하지 않는다. 의미 없는 무작위 문자열이어도 된다. 이런 토큰을 **불투명 토큰(opaque token)**이라 하고, 자원 서버는 받을 때마다 인가 서버에 "이거 유효해?"라고 물어야 한다(토큰 조회, introspection — RFC 7662).

이 물어보기를 없애려고 많이 쓰는 형식이 **JWT(JSON Web Token, RFC 7519, "jot"이라 읽음)**다. JWT는 토큰 안에 "누구에게, 무슨 권한을, 언제까지"를 직접 적고 **서명**을 붙인다. 자원 서버는 서명만 확인하면 인가 서버에 묻지 않고도 토큰을 믿을 수 있다.

### 구조 — 점(.)으로 나뉜 세 조각

JWT는 `헤더.페이로드.서명` 세 조각을 점으로 이은 문자열이다. 앞의 두 조각은 JSON을 **Base64URL(바이너리를 URL에 안전한 문자로 바꾸는 인코딩)**로 바꾼 것이다.

서명 방식은 크게 둘이다.

- **HS256(HMAC-SHA256)**: 발급자와 검증자가 **같은 비밀키**를 나눠 갖는다. 단순하지만, 검증하는 서버도 키를 가지니 그 서버도 토큰을 **만들 수 있다.**
- **RS256(RSA-SHA256)·ES256(ECDSA)**: 인가 서버만 **개인키**로 서명하고, 자원 서버는 **공개키**로 검증만 한다. 공개키는 보통 인가 서버가 **JWKS(JSON Web Key Set — 공개키 목록을 내려주는 주소)**로 공개한다. 자원 서버가 여러 개라면 이쪽이 안전하다.

## 상세 예시 — 토큰을 뜯어보고, 고쳐 보기

아래는 실제로 HS256으로 서명해 만든 JWT다(비밀키는 예시용 `demo-secret-do-not-use-in-prod-32b!`).

이 문자열이 하는 일: 주문 API에 `orders:read` 권한으로 15분간 들어갈 수 있다는 출입증이다.
```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.eyJpc3MiOiJodHRwczovL2F1dGguZXhhbXBsZS5jb20iLCJzdWIiOiJ1c2VyLTciLCJhdWQiOiJvcmRlci1hcGkiLCJzY29wZSI6Im9yZGVyczpyZWFkIiwiaWF0IjoxNzk0MzU4ODAwLCJleHAiOjE3OTQzNTk3MDB9
.yzc7MZSg_yOM5sU8mQAEhy59N_cdIJnZjGs5EYTXUSY
```
(보기 좋게 줄을 나눴지만 실제로는 한 줄이다.)

### 1단계 — 디코딩: 키 없이도 다 읽힌다

이 명령이 하는 일: 가운데 조각(페이로드)을 Base64URL 디코딩한다. Base64URL은 `-`·`_`를 쓰고 끝의 `=`를 생략하므로, 표준 Base64로 바꾸고 `=`를 채워 디코딩한다.
```bash
echo 'eyJpc3MiOiJodHRwczovL2F1dGguZXhhbXBsZS5jb20iLCJzdWIiOiJ1c2VyLTciLCJhdWQiOiJvcmRlci1hcGkiLCJzY29wZSI6Im9yZGVyczpyZWFkIiwiaWF0IjoxNzk0MzU4ODAwLCJleHAiOjE3OTQzNTk3MDB9' \
  | tr '_-' '/+' | awk '{ while (length($0) % 4) $0 = $0 "="; print }' | base64 -d
```
```json
{"iss":"https://auth.example.com","sub":"user-7","aud":"order-api",
 "scope":"orders:read","iat":1794358800,"exp":1794359700}
```

`iat`·`exp`는 1970-01-01 UTC부터 센 초(Unix 시간)다. `1794358800`은 2026-11-11 10:00 KST, `1794359700`은 그 15분 뒤인 10:15 KST다. **비밀키 없이 모든 내용을 읽었다.** 그래서 JWT 페이로드에는 비밀번호나 주민번호 같은 걸 절대 넣지 않는다.

### 2단계 — 위조: 권한을 늘려 보기

공격자가 읽기 권한에 쓰기 권한을 몰래 얹으려 한다. 페이로드의 `scope`를 `"orders:read orders:write"`로 바꿔 다시 인코딩하고, 서명은 원래 것을 그대로 붙인다.

| | 페이로드 scope | 붙어 있는 서명 | 서버가 다시 계산한 서명 |
|---|---|---|---|
| 원본 | `orders:read` | `yzc7MZSg_yOM5sU8…` | `yzc7MZSg_yOM5sU8…` ✅ 일치 |
| 위조 | `orders:read orders:write` | `yzc7MZSg_yOM5sU8…` (복사) | `OfdqCET1BIAm2es0…` ❌ 불일치 |

서버는 받은 `헤더.페이로드`를 자기 비밀키로 다시 서명해 붙어 온 서명과 비교한다. 페이로드가 몇 글자 바뀌자 계산 결과가 전혀 다른 값이 됐다. 공격자는 비밀키가 없으니 맞는 서명을 만들 수 없다. **401 Unauthorized.**

### 3단계 — 서명이 맞아도 확인할 것

서명이 맞는다는 건 "인가 서버가 만든 게 맞다"까지만 보장한다. 자원 서버는 이어서 클레임을 확인해야 한다.

이 코드가 하는 일: 서명 검증 뒤 받아들일 알고리즘·발급자·대상·만료를 명시적으로 검사한다(Python `PyJWT` 예시).
```python
import jwt  # PyJWT

claims = jwt.decode(
    token,
    key=SECRET,
    algorithms=["HS256"],              # 허용 알고리즘을 서버가 고정
    issuer="https://auth.example.com", # iss: 우리가 믿는 발급자인가
    audience="order-api",              # aud: 나(주문 API)에게 발급된 토큰인가
)                                      # exp: 만료는 기본으로 검사
if "orders:write" not in claims["scope"].split():
    raise PermissionError("403 Forbidden")
```

- **`algorithms`를 고정하는 이유**: 헤더의 `alg`는 공격자도 고칠 수 있다. `alg`를 `none`(서명 없음)으로 바꾸거나, RS256용 공개키를 HS256 비밀키처럼 쓰게 만드는 **알고리즘 혼동 공격**이 실제로 있었다. 토큰이 "나는 이 방식이야"라고 말하는 걸 믿지 말고, 서버가 허용 목록을 정한다.
- **`aud`를 보는 이유**: 사진 API용으로 발급된 토큰을 주문 API에 내밀면, 서명은 맞아도 받아들이면 안 된다.
- **401과 403 구분**: 토큰이 없거나 틀리면 401(인증 실패), 토큰은 맞는데 스코프가 모자라면 403(인가 실패)이다. 글 첫머리의 두 질문이 그대로 상태 코드가 된다.

## JWT의 대가 — 한번 준 출입증은 회수가 어렵다

JWT의 장점(서버가 아무것도 저장하지 않고 서명만 보면 됨)은 그대로 약점이 된다. 사용자가 로그아웃하거나 토큰이 유출돼도, **서명이 맞고 `exp`가 안 지났으면 자원 서버는 계속 받아 준다.** 서버에 "취소된 토큰" 기록이 없기 때문이다.

- **액세스 토큰은 짧게.** 유출돼도 피해 시간이 만료 시각까지로 묶인다.
- **리프레시 토큰(refresh token — 새 액세스 토큰을 받는 교환권)은 길게, 대신 인가 서버가 기록한다.** 인가 서버는 리프레시 토큰을 저장하니 언제든 취소할 수 있다. 로그아웃은 리프레시 토큰을 지우는 일이 된다.
- **리프레시 토큰 회전(rotation)**: 쓸 때마다 새것으로 바꾸고, 이미 쓴 것이 다시 오면 도난으로 판단해 전부 폐기한다(RFC 9700 권장 방식 중 하나).
- 즉시 차단이 꼭 필요하면 `jti`(토큰 고유 ID) 차단 목록을 두거나 불투명 토큰 + 조회 방식으로 돌아간다. 이때는 "서버가 아무것도 저장하지 않는다"는 장점을 일부 포기하는 셈이다.

브라우저에서 토큰을 **어디에 저장할지**도 중요하다. `localStorage`에 두면 페이지에 악성 스크립트가 끼어드는 XSS 공격 한 번에 토큰이 통째로 읽힌다. 그래서 토큰을 브라우저에 아예 주지 않고 앱 서버가 보관한 뒤 브라우저와는 `HttpOnly` 쿠키(스크립트가 읽을 수 없는 쿠키)로만 세션을 잇는 **BFF(Backend for Frontend)** 구성이 권장되곤 한다. 쿠키를 쓰면 이번엔 CSRF를 따져야 하는데, 이 이야기는 다음 글(CORS·CSRF·XSS)에서 이어 간다.

## 한눈에 정리

| | OAuth 2.0 | OIDC | JWT |
|---|---|---|---|
| 정체 | 권한 위임 **절차** | OAuth 위의 **로그인** 표준 | 토큰 **형식** |
| 답하는 질문 | 이 앱이 이걸 해도 되나? (인가) | 이 사람이 누구인가? (인증) | — (내용을 담고 위조를 막을 뿐) |
| 핵심 산출물 | 액세스 토큰 (형식 자유) | ID 토큰 (항상 JWT) | 서명된 클레임 묶음 |
| 꼭 지킬 것 | Auth Code + PKCE, `state` | ID 토큰의 `aud`·`nonce` 검증 | `alg` 고정, `iss`·`aud`·`exp` 검증, 비밀 정보 넣지 않기 |

## 한 줄 교훈

**OAuth 2.0은 "비밀번호 대신 범위가 정해진 출입증을 건네는 절차", JWT는 "그 출입증을 위조 못 하게 서명한 형식"이다** — 서명은 고치기를 막을 뿐 읽기는 막지 않고, 한번 준 출입증은 회수가 어려우니 짧게 발급한다.
